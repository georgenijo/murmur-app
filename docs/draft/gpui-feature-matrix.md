# GPUI feature and ownership matrix

Issue: #984. Baseline: `origin/gpui/00-phase0-exit`, inspected 2026-11-05.

This is the acceptance inventory for step 1.0 of the
[rewrite plan](gpui-rewrite-plan.md). The
[Phase 0 exit decision](../decisions/2026-11-05-gpui-phase-0-exit.md)
controls the route: **native parity first**, in the order Phase 1 → Phase 3 →
Phase 2 → Phase 4. Every main-window section reaches parity in the parallel
native build before the whole window switches. No partially ported main window
or React child view is required. Steps 0c, 0d, 1.7, 1.9, and 2.2 receive no work.

Current ownership follows [FEATURES](../FEATURES.md), its linked feature
contracts, [ARCHITECTURE](../ARCHITECTURE.md), and the source. Where an older
feature paragraph disagrees with the current implementation, the source wins:
Live Words exist; tray actions include Mode and next-recording controls; meeting
review is a transcript workspace, not a new summary-generation feature.

## How to use the matrix

- Current-module and existing-test cells cite repository files that exist on
  the baseline. A Rust source file in the test column means its inline tests;
  it does not claim native UI coverage. `none` means no identified automated
  coverage for that behavior or the explicitly named part of it.
- Phase 1 owners are responsibilities, not promises of new file paths. The
  core crate layout is decided in 1.1. “Core” means host-independent Rust with
  injected paths, permissions, task execution, and main-thread dispatch.
  “Host” means the native platform adapter. React remains a presentation client
  after Phase 1 wherever a row says so.
- The move column separates core/state extraction from native presentation.
  Prerequisites are gates for that row, not a claim that all listed steps run
  before Phase 1. Step 3.1 supplies the shared accessible control layer.
- **Every GPUI-test cell is a required future replacement, not an existing
  test name or a passing result.** Implement interaction, AX, golden, and native
  host checks as described. Keep backend tests through extraction. Retire a
  Vitest or Playwright assertion only after its corresponding replacement
  passes; a screenshot cannot replace a keyboard, ownership, or permission test.
- Acceptance uses a built native app on an isolated test bundle with synthetic
  dictations, meetings, calendar events, files, and knowledge. Never inspect
  production data or put private text, audio, clipboard contents, or selection
  into logs, goldens, screenshots, or recordings. OS permission, hardware,
  VoiceOver, and installed-update checks still need real native interaction.

Every row inherits these gates: one immutable recording-start configuration;
generation checks before async mutations; exactly-once final publication,
History, and counters; the single ordered transform entry point; secure-field
checks that fail closed; main-thread native geometry and unblocked UI dispatch;
one rdev listener with `set_is_main_thread(false)` before listening; and shutdown
that drains capture, helpers, and durable writes. Test each row with keyboard
and VoiceOver where applicable, and honor Reduce Motion and Reduce Transparency.
Move Rust-loaded frontend fixtures to a neutral location before deleting their
old owners, especially the overlay geometry and System Audio fixtures.

## Shared native component coverage (3.1 / #998)

The [accessible component layer](gpui-accessible-components.md) provides native
button, switch, field, dropdown, list, navigation and motion tests. These are
prerequisites for the screen acceptance flows below. No complete feature row
is marked passed and no Vitest/Playwright assertion is retired by component
coverage alone; later ports must list their concrete passing replacements.

## Phase 1 exit gates

Rows D01, H01, and R02 test pieces of these gates. Phase 1 is not done until
each gate passes as a whole.

- **Tauri-free core (1.1).** The core crate builds and runs its tests with no
  Tauri dependency in its dependency tree. The binary crate keeps the global
  allocator and the FoundationModels Swift build.
- **Headless control and delivery (1.2 and 1.3).** Use a test build that never
  creates the main webview, on a profile whose v1 migration is committed. It
  can arm, start, stop, cancel, auto-stop, and paste. Each completed recording
  produces exactly one durable History entry (none with `retainHistory=false`)
  and exactly one statistics update (also with `retainHistory=false`). Each file
  transcription produces one History entry and no statistics update. A finished
  meeting, a taught correction from the review window, and a Paste Last each add
  exactly one activity update. Opening, reloading, or reconnecting the main
  window and relaunching add nothing extra. Every case in the plan's v1
  migration table passes, and all counters, including activity counters, are
  unchanged across the upgrade and repeated launches.

## Decisions still needed during implementation

Behavior and responsibility are mapped above. These implementation choices are
not settled by Phase 0 and must not be mistaken for existing modules or tests:

- Step 1.1 chooses the core crate layout, AppContext interfaces, and Tokio
  runtime owner. Current paths are extraction sources, not final destinations.
- Step 3.5d chooses the native playback engine and ports the Web Audio clock,
  lookahead, underrun, and cancellation contracts. Step 3.5b also needs a native
  output-only sound-cue service; the plan does not name its audio API.
- Step 3.5e ports theme color compilation, JSONC/ZIP processing, and explicit
  Open VSX transport. Rust-owned appearance persistence in 1.5 alone does not
  replace those TypeScript implementations.
- Step 1.6 chooses the Rust updater implementation while preserving the
  installed-client feed/key and state machine. Step 2.4 proves identity and
  permission continuity with signed installed artifacts.

The native MacBook checks left open by Phase 0 remain open: VoiceOver speech,

# Independent reliability review: intermittent `device_unavailable` and flaky auto-paste

**Scope:** Murmur v0.30.1 on Mac16,7 (M4 Pro, 48 GB), fleet install `aa9472a5-43db-4d12-b90b-816a53cba2b0`
**Date:** 2026-08-11 · **Repo state:** `origin/main` @ `5c1cdad6` · **Type:** diagnostic review only — no changes made

Evidence drawn from source at that SHA, git/GitHub history, and the privacy-stripped fleet log for this install on `opti` (`~/murmur-logs/aa9472a5-…/events.jsonl`, 54,087 events, 2026-07-29 → 2026-08-11). No transcript content was retrieved; all queries returned summaries and content-free data fields only.

## 1. Executive conclusion

**These are two independent problems.** They share exactly one trait: both are *fail-closed guards working as designed with no visible feedback on the overlay*, so both present to an overlay-primary user as "the app silently did nothing."

**Problem 1 — most likely root cause:** The install has (or had) a pinned explicit microphone — an **Anker PowerConf C200** USB device — and that device intermittently drops out of the Core Audio inventory (USB/dock/display power cycling; two of five failure clusters immediately follow display-topology changes or wake). Since ~v0.24, a pinned device that is not in the live inventory **fails closed by explicit design** (issue #525: "A pinned device fails closed when it disappears"). The AUHAL→CPAL fallback runs correctly but passes the *same device ID* to both backends (`audio.rs:1517-1521`), so both independently and deterministically report `NoInputDevice` → `device_unavailable`. This is not a race, not stale-cache, not helper/host disagreement, and not AUHAL contaminating CPAL. The product bug is threefold: no device-level fallback or bounded re-resolution retry exists; the failure's fast path bypasses the `recording-initialization-failed` event so the overlay never flashes (0 occurrences in the log across 12 failures); and telemetry omits everything needed to prove which device was requested.

**Problem 2 — most likely explanation (composite):** There is no single defect. (a) The 7 refusals are the v0.30.0 target-PID guard doing its job, most visibly punishing **long toggle-mode recordings** — the PID is frozen at recording *start* (`commands/recording.rs:2671-2674`), so switching apps at any point during a 28-second toggle recording guarantees a refusal even if the user deliberately moved *to* their intended paste target. (b) Among the 29 "completed" pastes, "native CGEvent completed" is logged after two `CGEvent::post()` calls that return `()` with no delivery result (`injector.rs:289-301`); the 3 pastes that followed an AX "no focused element" answer are the prime candidates for silently dropped Cmd+V, and at 0 ms delay nothing gives focus time to settle. Neither the retry (fires only on construction/osascript `Err`, `injector.rs:213-221`) nor the osascript fallback (fires only on construction failure) can ever engage on a silent drop. (c) The overlay listens to `auto-paste-failed` nowhere (sole listener: `useRecordingState.ts:145`, rendered only in the main-window banner, `App.tsx`), so every refusal and failure is invisible during normal overlay-only use.

## 4. Hypothesis challenge

- **"Device resolution is racing a transient Core Audio inventory/default-device change" — falsified as the primary cause.** Failures persist across independent attempts 2.5 s, 39 s, and 5 min apart within a cluster (and one outage lasted ~10 minutes, 15:01–15:11); both backends run *independent, fresh* enumerations ~90 ms apart in separate helper processes and agree; and resolution latency is identical (66 ms) in success and failure — the enumeration completes and gives a definite "absent" answer. A micro-race cannot produce that shape. What survives is a weaker, compatible claim: *topology-churn periods* (wake, display connect) are when the pinned USB device is genuinely absent or re-enumerating. The 9–13 s fail→success flips fit a USB audio device waking/re-enumerating, not an app-side race.
- **"The target-PID guard accounts for some apparent paste failures" — survives, confirmed.** 7–8 refusals in the window, structurally silent on the overlay. The 28 s toggle-mode case shows the guard is stricter than its intent: it compares against recording-*start* frontmost, so it also refuses when the user deliberately settled into their intended target mid-recording.
- **"0 ms permits focus-sensitive editors to drop Cmd+V" — survives as supported-but-not-proven.** Direct evidence is absent (and can't exist with current telemetry). Circumstantial evidence is real: 3–5 pastes where AX said nothing was focused at keydown time, clustered at return-to-machine moments. Counterpoint kept honest: in the common flow the user never changes focus at stop, and 202 v0.28 pastes at 50 ms also showed zero *detected* failures — 0 ms is probably fine for the majority case; the risk is concentrated in the transition cases the AX "no focused element" events flag.
- **"Current telemetry mistakes 'event posted' for 'text delivered'" — survives, confirmed by source.** `CGEvent::post()` has no result; "completed" is logged unconditionally after posting; docs acknowledge it.
- **"Overlay users do not receive visible failure feedback" — survives, confirmed, and is broader than hypothesized.** It covers not just `auto-paste-failed` (no overlay listener) but also fast `device_unavailable` failures (the promise-rejection path bypasses `recording-initialization-failed`, so the overlay's existing `flashFailure` — which *was* built for this — never fires; zero emissions in the entire log).

## 5. Root-cause gaps (what's needed to reach proof; all content-free)

1. **Device-resolution telemetry** (closes P1): at each attempt log `microphone_mode: pinned|system_default` (no ID), `requested_present: bool`, `input_device_count`, `default_input_available`, and on failure the same fields from inside the helper. One boolean — `requested_present=false` while `default_input_available=true` — would convert the P1 root cause from "supported" to "proven." (#534's cached inventory is the natural home.)
2. **On-device check (one-off, no code):** read `settings.json` / localStorage `microphone` on the affected Mac to confirm the pinned Anker UID, and correlate `log stream --predicate 'subsystem == "com.apple.audio"'` or `system_profiler SPUSBDataType` during a repro window with the device's power state.
3. **Paste-outcome telemetry** (closes P2): one structured event per injection with `delay_ms`, `pid_match: bool`, `ax_state: editable|non_editable|unknown|none`, `posted: bool`, `verify: inserted|not_inserted|unverifiable` (see fix F6/F7), plus `target_is_self: bool` (was Murmur's own window frontmost at refusal — distinguishes "user checked history" from "user switched to Slack"). No bundle IDs, no text.
4. **Refusal provenance:** log `focus_changed_during: recording|processing` by sampling the PID once more at stop time (kept out of the guard decision; instrumentation only). This tells you whether refusals come from mid-recording switches (design tension) or stop-to-paste races (delay-sensitive).
5. **Overlay feedback audit metric:** count of failure events emitted vs. rendered surface. Currently unmeasurable because the events don't exist/fire.

Immediate mitigation for this user, zero code: repin to `system_default` (built-in mic never disappears), or raise the paste-delay slider to 50 ms — both already supported.

PR #530 (defer log-shipper enumeration during capture) should land regardless; no evidence was found that the log shipper's enumeration *caused* these failures (clusters don't require it, and enumeration can't remove a device from inventory), so it's hygiene, not the fix.

## 7. Test and rollout plan

**Deterministic unit/integration (CI):**
- Sidecar resolver: requested-UID-absent, empty-inventory, and no-default cases each yield `NoInputDevice` on both backends (extend existing `production.rs` tests); retry loop (F3) is bounded, cancellable mid-loop, and preserves owner-generation checks (model on `unconfirmed_termination_fails_closed…`, `audio_lifecycle.rs:2415`).
- Injector: ordering invariant test (clipboard → delay → PID → AX → post); conditional-delay logic (F4) as a pure function; refusal emits the target-changed message; retry never fires when `simulate_paste` returns `Ok`.
- Frontend: overlay renders flash/status for `auto-paste-failed` and for promise-rejection init failures (vitest; both are currently untested because untriggered).

**Native macOS smoke (Murmur Bench does not cover capture start or paste — it replays WAVs):**
- USB flap drill on a trusted Mac: pin a USB mic, unplug/replug and sleep/wake across dictation attempts; assert fail-fast + visible overlay flash + recovery-on-retry, and (with F3) that ≤1.5 s blips self-heal.
- Paste matrix: TextEdit (native), VS Code/Slack (Electron), Safari/Chrome contenteditable (web), Terminal, and a just-switched-Space case; each at 0 ms and 50 ms, hold-mode and toggle-mode, verifying actual insertion manually while the new outcome telemetry records.

**Fleet soak / A-B — isolating delay from the PID guard:** the guard refuses *before* the post, and refusals are separately logged, so compute delivery metrics **conditional on `pid_match=true`**. With F2 telemetry shipped: run 0 ms vs 50 ms (per-install toggle or alternating weeks) on the same v0.30.x guard code, and compare (i) `ax_state=none|unknown` rate at keydown, (ii) `verify=not_inserted` rate where verifiable, (iii) manual re-paste proxy (a Cmd+V keystroke of the same clipboard within 10 s — content-free, detectable from the existing key listener) — that proxy is measurable *today*, before F6. Do not compare against the v0.28 cohort; it lacked the guard and the telemetry.

**Acceptance criteria:** device: 0 both-backend failures without a corresponding actionable overlay flash; blip-window (≤1.5 s) failures self-heal ≥90%; startup p50 stays ≤250 ms (bench gate `quick` on the PR head per CLAUDE.md). Paste: refusal rate visible and explained; `ax_state=none` pastes < 1% at chosen delay; zero duplicate insertions; p95 paste stage ≤ 60 ms if 50 ms conditional delay adopted (#487's budget survives).

**Rollback conditions:** F3 rolls back if time-to-failure feedback regresses user-visibly (>2 s) or any cancellation/ownership test flakes; F4 rolls back if paste p95 exceeds #487 targets or the conditional path misfires (>5% of pastes taking the delay branch while `Editable`); F5 (if ever enabled) rolls back on a single wrong-device capture report — that criterion is absolute.

## Honest limits

The P1 root cause is one boolean short of proven (no post-v0.24 telemetry records the requested device; checking `settings.json` on the affected Mac closes it in minutes). For P2, whether any of the 29 completed pastes actually failed to insert is **unprovable with current instrumentation** — the three AX-flagged posts are suspects, not convictions, and it is genuinely possible that all 29 delivered and the entire perceived flakiness is the PID guard plus the overlay's silence. That possibility is itself the strongest argument for fixing feedback and telemetry before touching timing.
